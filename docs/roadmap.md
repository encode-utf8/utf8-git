## 1. 里程碑总览

原则：**每一期都必须产出可运行、可演示的东西**；先打通「看得懂」的闭环，再叠加「敢操作」的能力。

| 里程碑 | 名称 | 一句话目标 | 预估 | 状态 |
| --- | --- | --- | --- | --- |
| M0 | 立项与文档 | 想清楚做什么、怎么做，仓库可协作 | 1–2 天 | 🚧 进行中 |
| M1 | 只读最小闭环 | 登录 → 仓库列表 → 提交时间线，端到端可用 | 1.5–2 周 | ⏳ 未开始 |
| M2 | 只读增强 | 分支泳道 + PR/Issue 事件 + 过滤搜索 | 2 周 | ⏳ 未开始 |
| M3 | 交互操作 | 建分支 / 提 Issue / 合并 / 删分支（含安全护栏） | 2–3 周 | ⏳ 未开始 |
| M4 | 工程化与体验 | 性能、测试、国际化、可访问性、可观测性 | 2 周 | ⏳ 未开始 |
| M5 | 生态扩展 | 教学引导、多平台、插件与社区化 | 待定 | 💡 构想 |

## 2. M0 · 立项与文档

**目标**：把模糊想法变成可评审、可执行、可追踪的文档基线。

**交付物**

- [x] 公开开发仓库 `gitrail`（README、LICENSE、.gitignore）
- [x] 需求分析文档（用户故事、功能/非功能需求、验收标准、范围边界）
- [x] 技术分析文档（架构选型、API 策略、泳道算法、安全设计）
- [x] 实现路线（本文件）与开发记录、待办日志
- [ ] 本地开发环境约定（Node 版本、包管理器、提交规范）→ 随 M1 骨架落地

**退出标准**：文档评审通过；M1 任务清单可直接开工；仓库结构决策不再变更。

## 3. M1 · 只读最小闭环

**目标**：`登录 → 仓库列表 → 提交时间线` 全链路跑通，部署到公网可访问。

**任务分解**

| # | 任务 | 产出 | 验收 |
| --- | --- | --- | --- |
| M1-1 | 初始化 monorepo 骨架 | `apps/web` + `packages/*`、ESLint/Prettier、CI | `pnpm build` 与 CI 通过 |
| M1-2 | GitHub OAuth 登录 | Auth.js 接入、会话持久化、登出 | 未登录跳转、登录后回跳、令牌不出服务端 |
| M1-3 | 仓库列表 | `/repos` 页面、分页/排序、空状态 | 展示用户创建/参与的仓库 |
| M1-4 | GitHub 数据层 | GraphQL 客户端、缓存与限流处理 | 单仓库时间线 ≤3 次请求；命中限流有降级 |
| M1-5 | 时间线 v1 | 提交节点、虚拟滚动、节点详情 | 1000 提交滚动流畅；详情含作者/时间/SHA |
| M1-6 | 部署 | Vercel + 数据库、环境变量管理 | 公网可访问，冷启动 < 3s |
| M1-7 | 测试基线 | 关键路径单测 + 1 条 E2E | CI 全绿 |

**退出标准**：陌生用户无需文档即可完成「登录 → 打开仓库 → 看懂最近提交」；核心页面 Lighthouse 性能 ≥ 80。

## 4. M2 · 只读增强

**目标**：把「提交列表」升级为「分支故事」。

| # | 任务 | 产出 | 验收 |
| --- | --- | --- | --- |
| M2-1 | 泳道布局算法 | `packages/git-graph`（含单测） | 覆盖 merge/root/多父/rebase 等边界用例 |
| M2-2 | 分支泳道渲染 | SVG 分层渲染 + 虚拟窗口 | 50 分支 / 5000 提交可交互 |
| M2-3 | PR / Issue 事件接入 | GraphQL 聚合、时间线事件节点 | 事件与提交时间对齐，可跳转 GitHub |
| M2-4 | 过滤与搜索 | 作者/分支/事件类型/关键词 | 结果实时反馈，过滤 < 100ms |
| M2-5 | 时间缩放 | 近一周/一月/全部视图 | 缩放保持选中上下文 |
| M2-6 | 概念解释层 | 术语悬浮卡片、新手/进阶模式切换 | 可关闭，不干扰老用户 |

**退出标准**：能在一个屏幕上讲清「这个仓库最近发生了什么」；用户可复盘一次完整的分支生命周期。

## 5. M3 · 交互操作

**目标**：让新手在安全护栏内完成真实协作操作。

| # | 任务 | 产出 | 验收 |
| --- | --- | --- | --- |
| M3-1 | 操作框架 | 确认卡片组件、操作编排服务、审计表 | 所有写操作走同一管线 |
| M3-2 | 创建分支 | 基于提交/分支建分支、命名校验 | 成功后时间线即时更新 |
| M3-3 | 创建 Issue | 表单 + Markdown 预览 + 标签 | 成功后时间线出现事件 |
| M3-4 | 合并（PR 流程） | 建 PR → 可合并性检查 → 合并 | 冲突/不可合并有明确原因 |
| M3-5 | 删除分支 | 保护规则、影响预览、删除执行 | 默认/保护分支禁止删除 |
| M3-6 | 撤销与恢复 | 24h 恢复窗口、SHA 记录 | 恢复入口可用并说明限制 |
| M3-7 | 操作历史 | 审计查看页 + 等价 Git 命令 | 每条记录含结果与链接 |

**退出标准**：3 位非目标用户在无指导情况下完成一次「建分支 → 提 Issue → 合并 → 删分支」，且无一次误操作或困惑性失败。

## 6. M4 · 工程化与体验

| 方向 | 内容 |
| --- | --- |
| 性能 | 大仓库基准测试、服务端泳道缓存、按需加载 diff 详情 |
| 质量 | 单测覆盖率 ≥ 70%（核心包 ≥ 85%）、E2E 覆盖 5 条关键路径 |
| 体验 | 国际化（zh-CN / en）、深浅色主题、键盘可达性、移动端只读适配 |
| 可观测性 | 结构化日志、错误上报、限流与操作成功率看板 |
| 工程化 | 依赖更新、发布流程、环境隔离（preview / production） |

**退出标准**：上线运行 2 周无 P0 事故；核心操作成功率 ≥ 99%；具备对外发布说明与贡献指南。

## 7. M5 · 生态扩展（构想）

- **教学引导**：内置「Git 微课」路径，把操作与概念解释串联成群；
- **多平台**：抽象 Git Provider 接口，接入 GitLab / Gitea；
- **插件机制**：自定义时间线事件源（如 CI 结果、发布标签）；
- **团队视图**：组织级仪表盘、仓库健康度（僵尸分支、陈旧 Issue）。

## 8. 迭代节奏与工程约定

| 项 | 约定 |
| --- | --- |
| 迭代周期 | 1 周一个小迭代，每期结束对照本文件更新状态 |
| 分支模型 | `main` 保护；功能分支 `feat/<scope>`、修复 `fix/<scope>`；PR 合并前需 CI 通过 |
| 提交规范 | Conventional Commits（`feat/fix/docs/chore/test/refactor`） |
| Definition of Done | 功能可用 + 测试通过 + 文档更新 + 待办日志同步 + 无 lint 错误 |
| 变更记录 | 每次迭代在 [开发记录](development-log.md) 追加一条；决策在日志中注明理由 |
| 评审机制 | 重要决策（架构、数据模型、安全）以文档形式提交 Issue 讨论后定稿 |

## 9. 度量指标（North Star 与护栏）

| 类型 | 指标 | 目标 |
| --- | --- | --- |
| 北极星 | 用户完成一次「时间线浏览 → 至少一个有效操作」的比例 | 持续提升 |
| 体验 | 首屏可交互时间 / 时间线滚动帧率 | < 2s / ≥ 50fps |
| 安全 | 误操作率、可恢复率 | 误操作 < 1% 且 100% 可追溯 |
| 效率 | 登录到看懂仓库（首次会话停留并产生滚动/展开行为） | 中位数 < 5 min |
| 工程 | CI 通过率、平均恢复时间（MTTR） | ≥ 95% / < 1h |

## 10. 优先级与调度原则

1. **闭环优先**：宁可牺牲功能数量，也要保证「登录→时间线」端到端可用；
2. **安全前置**：写操作相关的能力必须与护栏同期交付，不允许「先上功能后补保护」；
3. **可视化优先于管理功能**：与叙事无关的功能进入 Backlog；
4. **一切以真实仓库验证**：每个里程碑至少用 3 个真实仓库（小/中/大）做验证。
