## 2. 上线运行 2 周无 P0 事故

### 2.1 事故分级（本仓库约定）

| 级别 | 定义                                      | 例子                                         |
| ---- | ----------------------------------------- | -------------------------------------------- |
| P0   | 服务整体不可用、数据丢失 / 串权、安全事件 | 时间线全量 5xx、令牌或会话泄露、未授权写操作 |
| P1   | 核心链路受损但有替代路径                  | 单仓库加载失败、写操作全量失败但只读可用     |
| P2   | 局部体验问题                              | 布局错位、文案错误、非核心接口偶发失败       |

### 2.2 数据源（M4-1 已就绪）

- **结构化日志**：12 个 API 路由经 `withObservability` 包裹，每条请求落
  `http_request` 日志（`route` / `method` / `path` / `status` / `durationMs` / `requestId`）；
  `status ≥ 500` 或抛错时额外上报 `unhandled_error`（M4-1，TODO-241）。
- **错误上报**：配置 `ERROR_REPORT_ENDPOINT` 后，未捕获错误与 5xx 会 POST 到该端点
  （尽力而为，上报失败只记 warn，不影响响应）。未配置时以平台侧日志为准。
- **请求关联**：响应头 `x-request-id`（可复用调用方传入值），一次请求的多条日志可串联。
- **脱敏**：日志字段先经 `lib/redact.ts` 脱敏（连接串 / GitHub 令牌 / 敏感键名）再落盘，
  事故排查可直接贴日志。

### 2.3 核对方式

从真实部署日起连续 14 个自然日，P0 计数为 0 即达标；出现 P0 需记录事故单（现象 / 影响面 /
恢复时间）并顺延一个观察周期。核对人：发布负责人；核对产出记入 development-log。

## 3. 核心操作成功率 ≥ 99%

### 3.1 度量口径（一次定义，照方执行）

- **核心操作**：六个写操作——创建分支、创建 Issue、创建 PR、合并 PR、删除分支、恢复分支。
  账号级操作（撤销授权 / 清除数据）为低频管理动作，单独观察、不计入本指标。
- **数据源**：写操作审计表。`runOperation` 对每次真实执行写 `started` → 终态
  （`succeeded` / `failed`）两条记录；幂等键命中窗口内已成功记录时**直接回放、不写任何新记录**。
- **分母口径**：按幂等键收敛（`latestPerIdempotencyKey`）后只数终态：
  `分母 = succeeded + failed`。重放不新增记录，天然不进分母——避免用户重复点击
  同时虚高分子与分母。校验失败（400 / 401 / 429）发生在 `started` 之前，同样不进分母；
  进分母的都是「真正尝试过的执行」，失败主要来自 GitHub 侧（冲突 / 限流 / 不可达）。
- **公式**：`成功率 = 收敛后 succeeded ÷ (succeeded + failed)`，按自然日聚合；
  目标 ≥ 99%，即万次执行最多 100 次失败。
- **导出与核对工具**（已具备）：操作历史页 + `/api/account/audit/export?format=csv|json`
  （预取 3000 条、最多导出 1000 条操作，与历史页同一收敛口径）。

### 3.2 已固化的验证（上线前预检）

- 契约层 E2E（`e2e/operations-api.spec.ts`）固化成功 / 重放 / 冲突三条路径的
  HTTP 语义（201 / 200 replayed / 422），成功率口径依赖的状态机有测试保护。
- 口径相关的纯逻辑（收敛、重放窗口、限流窗口）均有单测。
