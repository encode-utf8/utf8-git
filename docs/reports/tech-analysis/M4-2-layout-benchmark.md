# M4-2 泳道布局基准（1000 / 10000 节点）

> 对应 [待办日志](../../todo.md) TODO-242；脚本 `packages/git-graph/src/layout.bench.ts`。

## 1. 目标

回答两个问题：万级提交（大仓库）下时间线的泳道布局与窗口切片是否仍在可接受范围内；
耗时是随节点数近似线性增长，还是藏着平方级 / 全量扫描的隐患。

## 2. 方法

- 输入用 `packages/git-graph/src/synthetic-history.ts` 的确定性合成历史，覆盖两类结构：
  - **深链**：单泳道、无分支，考察纯节点规模；
  - **分支合并**：主干 + 功能分支 + merge 提交，并发度分别取默认 6 与满并发（泳道数 = 分支数 + 1）。
- 规模按 `branches × (commitsPerBranch + 1) + 1` 精确取 1000 与 10000 节点。
- 采样：预热 5 轮后采样 25 轮，报告 min / median / p99（ms）；切片窗口 21 行，与
  `apps/web/lib/virtual-window.ts` 的视口（600px / 76px 行高 + overscan）一致。
- 运行：

```bash
pnpm --filter @utf8-git/git-graph bench           # 输出下表
pnpm --filter @utf8-git/git-graph bench -t 10000  # 只跑万级用例
```

- 环境：Windows / Node v24.21.0 / pnpm 12。绝对值随机器变化，关注 median、p99 与相对倍率。

## 3. 结果（优化后）

| 规模  | 场景                   | 泳道 | 布局 min | 布局 median | 布局 p99 | 切片 median | 切片 p99 |
| ----- | ---------------------- | ---- | -------- | ----------- | -------- | ----------- | -------- |
| 1000  | 深链                   | 1    | 0.733    | 0.778       | 1.267    | 0.003       | 0.048    |
| 1000  | 分支合并（默认并发 6） | 7    | 1.616    | 1.838       | 2.587    | 0.003       | 0.004    |
| 1000  | 合并风暴（满并发）     | 28   | 2.270    | 2.672       | 3.460    | 0.007       | 0.039    |
| 10000 | 深链                   | 1    | 6.428    | 7.545       | 10.15    | 0.001       | 0.106    |
| 10000 | 分支合并（默认并发 6） | 7    | 14.81    | 16.86       | 42.30    | 0.004       | 0.006    |
| 10000 | 合并风暴（满并发）     | 100  | 117.6    | 122.4       | 196.6    | 0.028       | 0.054    |

## 4. 关键发现

1. **布局耗时随节点数近似线性**：深链 1000 → 10000 节点，median 0.78ms → 7.5ms（约 10 倍，
   与节点数比一致），说明内核没有平方级路径。分支合并（默认并发 6）同为个位数到十几毫秒。
2. **窗口切片曾与总线段数成正比**：切片只产出窗口内的线段（元素量有界），但旧实现用
   `Array.filter` 扫描**全部**线段，万级满并发下单次约 6.4ms —— 虽仍在 60fps 帧预算内，
   但每帧都要付这份成本，且把「窗口化」的收益抵掉了一大截。
3. **改为按行二分定位后**：`computeLaneLayout` 产出的 `segments` 本就按 `row` 升序，
   切片只需二分出窗口覆盖的连续区间（见 `layout.ts` 的 `firstSegmentAtOrAfter`）。
   万级满并发切片 median 6.379ms → 0.028ms（约 220 倍），且不再随仓库大小增长。
   依赖的升序不变式已由 `layout.test.ts` 的用例固定（并用逐窗口与朴素过滤对比保证等价）。
4. **满并发万级整体布局约 120ms**：这是**一次性**成本（只在切换分支 / 加载更多时触发，
   滚动时不重算），可接受；但若要在服务端做泳道缓存，应据此评估缓存粒度。

## 5. 护栏与下一步

- CI 护栏 `layout.perf.test.ts` 已覆盖 5051 与 10000 节点：布局落在预算内、切片落在 60fps
  帧预算内且元素量只与窗口大小相关（阈值留足 CI 抖动余量，精确数字看基准脚本）。
- 下一步（roadmap M4 性能方向）：服务端泳道缓存 / 增量布局，避免大仓库切换分支时全量重算。
